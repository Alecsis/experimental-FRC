# Architecture Rules — Rationale & History

Rationale layer behind `CLAUDE.md`'s `## 📐 Architecture Rules`. The rule statements in `CLAUDE.md` are the enforceable contract; this file is *why* each rule exists, what's been decided about its edges, and what's still an open, accepted gap. Update this file (not `CLAUDE.md`) when a session establishes or revises an architecture decision.

## Rule 1 — Strict Hardware Isolation

No vendor hardware APIs (CTRE Phoenix, REVLib, etc.) are allowed in standard subsystem files. They must live strictly inside `*IOReal.java` implementations.

- **Sanctioned vendor exception (decided 2026-07-16):** `subsystems/CommandSwerveDrivetrain.java` and `utility/simulation/MapleSimSwerveDrivetrain.java` are the **singular** sanctioned exception to this rule. They are CTRE Tuner X / swerve-generator output and stay vendor-inline rather than wrapped in a `DriveIO` — regenerating them from Tuner X would otherwise conflict with a hand-maintained IO wrapper. Every other file must stay vendor-free.
- **Utility layer is NOT exempt.** `utility/HubActiveState.java` used to import `com.ctre.phoenix6` (`HootAutoReplay`, `Utils`) directly for Hoot auto-log/auto-replay. That hookup is now isolated in `utility/HootReplayBridge.java` (package-private, the only file in `utility/` that touches Phoenix 6); `HubActiveState.java` itself is vendor-free.
- **Blast radius, accepted (2026-07-16 verification scan):** `RobotContainer.java` and `Telemetry.java` import `com.ctre.*` (`SwerveRequest`, `SwerveDriveState`, `SignalLogger`). This is the *blast radius* of the sanctioned `CommandSwerveDrivetrain` exception — its public API is vendor-typed — not a new Rule 1 leak. Accepted; wrapping would mean wrapping the drivetrain itself, which we decided against.
- **`RobotMotor` shared utility, adopted (2026-07-18, mentor-directed, full design at `docs/claudex/design/robotmotor-refactor.md`):** prompted by the ninth session's Lynk 2026 structural comparison (`LynkMotor`/`LynkSubsystem` wrap CTRE hardware directly, no IO-interface split). A literal copy of that pattern was rejected — it would delete the sim/replay seam `run_headless_sim.py` and both JUnit tests depend on. Instead, `utility/RobotMotor.java` (`extends TalonFX`) gives `*IOReal.java` files Lynk-style construction ergonomics (`MotorConfig` bundling, optional debounced stator-current `SafetyTripConfig` for early/soft warning — logging only, never `setControl()`, never a substitute for subsystem-owned jam logic) while staying instantiable only from inside `*IOReal.java`. `IntakeIOReal.intakePivot`/`roller` and `ShooterIOReal.shootMotor`/`indexMotor` migrated; `IntakeIOReal.roller` deliberately has `safetyTrip = null` (Intake already owns tuned jam-recovery on that exact signal — see Rule 3's "two writers, same tick" entry below). `ShooterIOReal.agitator` (a `TalonFXS`, not `TalonFX` — the only `TalonFXS` in the codebase) was excluded from this pass rather than building a parallel wrapper class for one motor instance; revisit if a second `TalonFXS` motor appears. `IntakeIO`/`ShooterIO` interfaces, both `*IOSim.java` files, and `@AutoLog` inputs structs are all unchanged. **Verification limitation, stated plainly:** `run_headless_sim.py` and both JUnit tests run in `Constants.Mode.SIM`, which never constructs `IntakeIOReal`/`ShooterIOReal` — `compileJava` proves the migration builds, but `RobotMotor`'s behavior against real CAN hardware is UNVERIFIED until next robot bring-up.

## Rule 2 — Singleton Subsystems

Every subsystem and the `Superstructure` must implement the Singleton pattern (`private` constructor and `public static Subsystem getInstance()`). No history beyond the rule itself — this has held unchanged since the Intake/Shooter/Vision refactors (see `docs/claudex/history.md`).

- **Clarified, not changed (2026-07-18, `TrajectoryErrorTracker`):** this rule scopes to subsystems and `Superstructure` specifically — it does not extend to every stateful utility class. `utility/TrajectoryErrorTracker.java` is deliberately a plain class, constructed and owned by `RobotContainer` (`() -> drivetrain.getState().Pose` handed in at construction), not a singleton with `getInstance()`. It is neither a `Subsystem` nor part of `Superstructure`'s arbitration, takes no scheduler requirement, and exactly one place (`RobotContainer`) ever needs a handle to it — a singleton would only have bought order-dependent unit tests (static state persisting across JUnit methods in the same JVM) for no benefit. Precedent for future non-subsystem stateful utilities: default to plain-class-owned-by-constructor, reach for singleton only when multiple unrelated call sites genuinely need the same instance.

## Observability instrumentation pattern — trajectory error tracking (established 2026-07-18)

`utility/TrajectoryErrorTracker.java` computes lateral/longitudinal/heading error between PathPlanner's per-loop setpoint and the measured drivetrain pose, logged via AdvantageKit (`Trajectory/*` topics). Full design: `docs/claudex/design/trajectory-error-instrumentation.md`. Two decisions here are meant to generalize to future instrumentation work, not just this one tracker:

- **Vendor integration via the existing push seam, never a new import.** `CommandSwerveDrivetrain.configureAutoBuilder()` already registered two `PathPlannerLogging` static callbacks (`setLogActivePathCallback`/`setLogTargetPoseCallback`) before this tracker existed, purely to log `Odometry/Trajectory`/`Odometry/TrajectorySetpoint`. The tracker plugs into those two *existing* callbacks with two delegating lines rather than adding any new PathPlanner import, subclassing `PPHolonomicDriveController`, or wrapping `FollowPathCommand`. `TrajectoryErrorTracker` itself imports only WPILib geometry + AdvantageKit — constructible and unit-testable with zero vendor stack. Consequence: if PathPlanner is ever swapped for Choreo or a hand-rolled follower, only the two lambdas move: the tracker, its topic schema, and any AdvantageScope layouts built on it survive unchanged. **Future observability work on vendor-driven behavior (PathPlanner, Phoenix 6, etc.) should look for an existing push callback/hook first before adding a new vendor import to read internal state.**
- **Explicit reordering over hidden snapshotting, for cross-thread-adjacent timing fixes.** The tracker needs the setpoint PathPlanner produced *this* loop paired with a same-instant measured pose. The chosen fix is placement: `Robot.robotPeriodic()` calls the tracker's periodic hook (via `RobotContainer.trajectoryTrackerPeriodic()`) *after* `CommandScheduler.run()`, not before — a one-line, greppable ordering decision at the exact place it matters. The rejected alternative (snapshotting the pose inside the `PathPlannerLogging` callback itself) would have made correctness depend on an invariant invisible at every call site. **Precedent: when two data sources need to agree on "this loop," prefer moving a call site to an explicit, visible position over burying a snapshot inside a callback whose firing context isn't obvious from its own code.**
- **Known limitation, partially mitigated (root-caused 2026-07-18, mitigation applied and measured same day — see `docs/claudex/history.md`'s twelfth-session entry):** `CommandSwerveDrivetrain.getState().Pose` is refreshed by CTRE Phoenix 6's native `SwerveDrivetrain.OdometryThread` (JNI-backed, `Utils.getCurrentTimeSeconds()` → native `UtilsJNI.getCurrentTimeSeconds()`), a clock domain independent of WPILib's paused/stepped `SimHooks` clock the rest of the robot loop runs on in JUnit-driven sim tests — confirmed from decompiled CTRE source, not inferred. A controlled before/after sim comparison (PathPlanner PID gain change) produced run-to-run noise comparable to the tested effect size across repeated trials of *identical* code. **Mitigation applied:** `CommandSwerveDrivetrain.startSimThread()` now raises all 22 odometry-relevant StatusSignals to 250 Hz via `BaseStatusSignal.setUpdateFrequencyForAll(...)` under `Utils.isSimulation()`, per CTRE's own documented recommendation for simulated-CAN-latency mitigation. Measured same-auto A/B (3 trials/condition): RMS lateral-error spread ~0.177m before → ~0.094m after (mean also roughly halved). **This narrows, does not eliminate, the variance** — no public CTRE API replaces or synchronously steps the native odometry thread itself, so full determinism remains out of reach without an architecture change (explicitly out of scope). Full writeup: `docs/claudex/design/sim-timing-determinism.md`. **Any future milestone that wants to prove a gain change helped or hurt still needs either multiple averaged trials or a fully deterministic unit test that stubs the pose/setpoint suppliers directly — not a single sim run.**

## Simulation fidelity tradeoffs (established 2026-07-18)

MapleSim's field-obstacle model (`Arena2026Rebuilt`, a vendored library class) defaults to treating the 2026 field's Bump/ramp region as either a fully solid collider or no collider at all — `dyn4j` (its physics engine) has no height axis, so it cannot represent a drivable ramp as its own category. The default (`AddRampCollider=true`) blocked every PathPlanner auto that crosses the Bump entirely, confirmed both architecturally (library source) and geometrically (`Left Bump Start.path`'s waypoints sit inside the collider's footprint) and validated via a controlled A/B JUnit trial (0.0m vs. 4.78m of path progress, collider on vs. off). **Decision: `SimulatedArena.overrideInstance(new Arena2026Rebuilt(false))`, sim-only, inside `MapleSimSwerveDrivetrain`'s constructor** — prioritizing autonomous-development usability (the sim's actual purpose this offseason) over field-obstacle realism in a spot where the physics engine can't model the real behavior faithfully either way. This is a deliberate, generalizable precedent: **when a vendored sim library's field/obstacle model can't represent something faithfully, prefer the configuration that best serves what the sim is actually being used for (here: autonomous path-following development), not whichever default the library ships with.** A community add-on (`RobotBumpSim`) exists that adds real climb/stall/slide ramp physics on top of this same "collider off" starting point, but was evaluated and not adopted (unmaintained ~4 months, would need real integration/tuning work) — revisit only if bump-climbing dynamics themselves become strategically important.

## Pose ownership (established 2026-07-19)

Multiple independent authorities can write the drivetrain pose, and before this was made explicit they silently raced — a sim-convenience spawn stomped `AutoBuilder`'s path-start seed one loop later, teleporting the robot 12.72 m mid-autonomous (full evidence: `docs/claudex/history.md`'s fifteenth-session entry). **Exactly one authority owns the pose in any given robot state:**

| Authority | Owns | Guard |
|---|---|---|
| `CommandSwerveDrivetrain.maybeApplySimPracticeSpawn()` (MapleSim practice spawn) | the initial **disabled** simulation pose | `mapleSim != null` && `DriverStation.isDisabled()` && one-shot latch |
| `AutoBuilder`/PathPlanner (`resetOdom`) | **autonomous** pose initialization | fires inside `PathPlannerAuto.initialize()` when `"resetOdom": true` |
| `Vision` (`addVisionMeasurement`) | continuous vision-based **corrections** | pose-estimator fusion, never a hard reset |

**The invariant: a simulation convenience feature must never overwrite an enabled robot's pose.** Generalizes past this one call site — any future sim-only or debug-only pose write (a reset-to-origin dashboard button, a replay seek, a test fixture) must be gated on `isDisabled()`, not merely on "we haven't done it yet."

Two implementation details are load-bearing and must not be "simplified":

- **The one-shot latch is deferred, not consumed.** `m_hasAppliedSimPracticeSpawn = true` is set *inside* `DriverStation.getAlliance().ifPresent(...)`. The alliance is genuinely unknown until the DS connects (`getAlliance()` returns empty at construction), so the spawn must poll for *both* disabled-state and alliance-known. Hoisting the assignment out of the lambda would look like a harmless cleanup and would silently cost a cold-DS session its practice spawn for the rest of the robot-code lifetime. Pinned by `SimSpawnPoseOwnershipTest.spawnIsDeferredNotConsumedWhenAllianceFirstResolvesWhileEnabled`.
- **Separate flags for separate responsibilities.** The bug existed because the spawn shared `m_hasAppliedOperatorPerspective` with the operator-perspective logic. That flag's guard is an OR (`!m_hasAppliedOperatorPerspective || isDisabled()`) whose left half stays true until the alliance first resolves — which, on a cold DS attaching straight into auto, is the first *enabled* tick. **Precedent: never reuse an existing "have we done this yet" flag for a second, unrelated one-shot** — the two responsibilities will eventually need different guards, and the coupling is invisible at the call site.

**Rule 2 note:** `CommandSwerveDrivetrain` is *not* a singleton — it is constructed by `TunerConstants.createDrivetrain()` and held as a `public static` field on `RobotContainer`. This is CTRE Tuner X generated structure (the same generated-output exception Rule 1 already grants it), not a Rule 2 violation to go fix. Tests needing an isolated drivetrain call the factory directly, which is safe because `build.gradle` sets `forkEvery = 1` (fresh JVM per test class).

## Rule 3 — Centralized States

The `Superstructure` coordinates complex multi-subsystem states via a `SuperstructureState` enum (`OFF`, `INTAKING`, `EJECTING`, `STOWED`, `ALIGNING`, `SHOOTING`) and a `periodic()` switch-case that commands Shooter/Intake/Vision directly.

- `shootCmd()`/`shootingSequence(double)`/`intakeCmd()`/`intakeSequence(double)` are thin Command bridges kept only because `RobotContainer`'s `whileTrue` binding and PathPlanner's NamedCommands both require real Command objects — the actual arbitration logic lives in `periodic()`, not in composed Commands. **`intakeSequence(double)` added 2026-07-19:** `intakeCmd()` (`Commands.startEnd`, built for a teleop hold binding) never finishes on its own — fine for teleop, but registered directly as a NamedCommand it silently hung every PathPlanner auto that used it inside a `"parallel"` block (which requires every branch to finish) forever after that block's other branch completed. `intakeSequence(double timeoutSeconds)` (`intakeCmd().withTimeout(timeoutSeconds)`) is the bounded, NamedCommand-safe variant — same shape as the already-existing `shootingSequence(double)`. **General lesson: any `Commands.startEnd`/hold-style bridge Command must get its own bounded sibling before it's registered as a NamedCommand — a hold command with no caller to release it will hang a `"parallel"` auto block silently, in sim and on real hardware alike.** Found via `docs/claudex/history.md`'s thirteenth-session auto-regression-suite work, not from a teleop report.
- Subsystems themselves still only handle their own immediate mechanism control (e.g. `Intake.agitatePivot()` stays owned by `Intake`; `Superstructure` schedules/cancels it as a unit rather than reimplementing its oscillation).
- **Known, accepted gap (2026-07-16 verification scan):** `Superstructure.shootCmd()` declares its requirement (`this`); `shootingSequence()` and `Intake.agitatePivot()` declare **no scheduler requirements**, and `Superstructure.periodic()` writes mechanism setpoints without requirements. Safe today by binding discipline, not enforcement. **Trigger to revisit:** first observed "two writers, same tick" conflict. Full analysis in the vault Deep Dive, Part II §6.1.
- **Trigger fired (2026-07-17, sixth session):** the intake jam-recovery migration's design investigation found the predicted conflict — `RobotContainer`'s old `"Intake Start Sequence"` NamedCommand called `intake.intakeJamReverse()` directly, bypassing `Superstructure` entirely, while `Superstructure.periodic()`'s `OFF` case unconditionally wrote `intake.setRoller(Roller.STOP)` every tick regardless of what any other caller was doing — a real second writer fighting the auto command on the same mechanism, same tick. **Resolved by elimination, not enforcement:** the fix (commit `d66d9a6`) routed `"Intake Start Sequence"`/`"Intake Stop"` through `superstructure.intakeCmd()`/`stowCmd()` instead, making `Superstructure.periodic()` the sole writer to `Intake` during `INTAKING` — no scheduler `requirements()` were added anywhere. The gap itself (no formal requirements enforcement) is still open and still accepted; this only closed the one instance that had actually manifested. Any *future* direct-mechanism-call NamedCommand or binding that bypasses `Superstructure` while it's active would reopen the same class of conflict — formal `requirements()` enforcement is still the queued fix if that happens again, see the reference-pattern adoption queue below.

## Auto regression testing pattern (established 2026-07-19)

The PathPlanner auto regression suite (`src/test/java/frc/robot/auto/`, design doc `docs/superpowers/specs/2026-07-18-auto-regression-suite-design.md`) established a few generalizable decisions for any future test that needs an auto to *actually run and move*, not just construct:

- **One JUnit class per auto, never a `@ParameterizedTest` looping over several.** `build.gradle`'s `forkEvery=1` exists specifically because Vision/Intake/Shooter/Superstructure are singletons with no reset hook (see `RobotLifecycleTest`'s own comment) — a parameterized loop over multiple autos in one class would run them all in one JVM/one set of singletons, exactly the leak `forkEvery=1` exists to prevent.
- **Real time, not `SimHooks`-accelerated time, for any test that needs the robot to physically move.** CTRE's `SwerveDrivetrain.OdometryThread` samples a real-time native clock independent of `SimHooks`' simulated clock (see the Observability instrumentation pattern section above). A `SimHooks.pauseTiming()`/`stepTiming()` loop with no real wall-clock delay between steps starves that native thread and leaves the reported pose frozen — confirmed empirically, not theorized. **Pattern:** use `pauseTiming()`/one `stepTiming()` call only for the brief, deterministic window needed to schedule a command safely (see next bullet), then `resumeTiming()` and poll with real `Thread.sleep()` for the rest of the run.
- **Never call `CommandScheduler.getInstance().schedule()` from the test thread while running in real time.** The robot thread concurrently calls `CommandScheduler.run()` once real time is flowing — scheduling from the test thread at the same time is a genuine data race on a non-thread-safe `Set`. Schedule while `SimHooks` is still paused (robot thread blocked), *then* switch to real time. From that point, the test thread should only *read* scheduler/pose state (matching `RobotLifecycleTest`/`SuperstructureEjectingTest`'s own existing read-only cross-thread access), never mutate it again.
- **Prefer post-hoc `.wpilog` analysis over live `NetworkTables` polling for anything transient.** A live poll of a single-tick AdvantageKit boolean flag (`TrajectoryErrorTracker`'s `SetpointFresh`) reliably missed real pulses due to poll/tick aliasing between the test thread's own cadence and the robot's periodic loop. The wpilog captures every tick synchronously from the actual robot loop and has no aliasing problem. Use WPILib's own `edu.wpi.first.util.datalog.DataLogReader`/`DataLogRecord` (already a transitive dependency, the same classes AdvantageKit's `WPILOGReader` uses internally) rather than a hand-rolled binary parser. **Entry names in the wpilog carry AdvantageKit's `/RealOutputs/` (or `/ReplayOutputs/`) prefix** — the raw string passed to `Logger.recordOutput()` is not the logged name; confirm the real name via `python SKILLS/parse_akit_log.py <log> --grep <keyword>` rather than assuming.
