### New finding — Disturbance Report **Finding 4 resolved** (this is the session's most durable result)

The severe 2.0 m run has always been the outlier: largest disturbance, *best* numbers (mean error 0.10 m, best
speed delivery). This session adds the missing piece — its **feedback magnitude also stays low (~0.9 m/s** vs
5.8–6.7 m/s elsewhere), in both experiment arms.

Mechanism: `Trajectory/Error*` is computed **estimator-pose vs setpoint**. `setSimulationWorldPose()` moves the
physics body without informing the estimator, and the 2 m displacement then exceeded
`Constants.kMaxVisionJumpMeters = 1.0`, producing the **242 consecutive vision rejections** the Disturbance

2 m off-path while the error signal read near zero and the controller stayed calm.

**The severe run is not evidence of disturbance recovery. It is evidence of _blind_ tracking**, and it ties the
anomaly directly to the F5 vision-lockout gap. The Disturbance Report flagged this as needing a re-test after the
chassis-PID fix; it is answered without one.

## Why it changed

The prior session's handoff named one next action: isolate the first 1.5 s of the control run. Doing so showed the initial error is **not** a drivetrain-delivery problem at all.

At `t=0`, before the robot has moved: position error **0.000 m** (pose == setpoint exactly), but heading **156.6°** against a trajectory setpoint of **78.3°** — and `2 x 78.2957 = 156.59`, where 78.2957° is `Left Trench Neutral`'s own `idealStartingState.rotation`. That 78° error hits chassis rotational `kP=3` and produces **-4.100 rad/s** of feedback on the very first sample (exact match). The robot spends ~0.7 s spinning rather than translating, accumulating **0.61 m** of position error, which then feeds translation `kP=5` into ~3 m/s of correction — saturation, then the already-documented brownout loop. Every previously measured symptom is downstream of this.

**Mechanism, located by staged diagnostic rather than inferred:**

```
before reset:       body=-22.054  pigeon= -8.720  estimator= -8.720
immediately after:  body= 78.296  pigeon=-22.052  estimator= 78.296   <- reset is CORRECT
after step 1:       body= 76.934  pigeon=-22.052  estimator= 78.296   <- still correct
after step 2:       body= 76.934  pigeon= 76.932  estimator=177.280   <- CORRUPTED
```

`resetPose` itself was never wrong. `MapleSimSwerveDrivetrain` drives the sim Pigeon's RAW yaw off the physics body, so a teleport leaves the Pigeon stale for a tick or two; when it catches up it steps ~99° at once, and CTRE's odometry — which integrates gyro **deltas** — folds that teleport artifact in as real rotation. Result: `reported = 2*target - heading_before`.

**One falsified attempt, reverted before the working fix:** syncing the gyro *before* `super.resetPose` without waiting changed nothing on the real path (still 156.6° at t=0), because the odometry thread had not yet refreshed the signal. Reverted via `git checkout`, then replaced with the wait-based ordering.

### 4. New root cause: uncommanded drift between path segments

The corrected baseline made a previously invisible defect legible. On the **full** `LT Neutral` auto,
lateral error still spiked to 1.608 m at t=5.00 s while the isolated segment tracked to 0.068 m.
Traced with numbers, not inference:

- `SetpointFresh` goes false at t=2.04 s and true again at t=4.98 s — a **2.94 s gap with no path
  following**.
- At t=2.04 the robot is **0.060 m** from `Left Trench Start`'s designed endpoint. Tracking was fine.
- It then keeps driving at **0.862 m/s** — exactly that path's `goalEndState.velocity` of 0.85 —

Mechanism confirmed from PathplannerLib 2026.1.2's decompiled `FollowPathCommand.end()`, which
**deliberately** skips zeroing the drivetrain when `goalEndState.velocityMPS() >= 0.1` ("this allows
interrupting the command to smoothly transition into some auto-alignment routine"). That contract
holds only when the next path starts immediately; inside a `parallel` block it does not, because the
block waits for its slowest branch — here `Intake Start Sequence`, `intakeCmd().withTimeout(5.0)`
with no early exit.

**This is not simulation-specific.** It follows entirely from PathplannerLib scheduling plus the
`.auto` structure, so it happens identically on real hardware.
